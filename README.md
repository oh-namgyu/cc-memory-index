> **한글 요약** — Claude Code 자동 메모리의 `MEMORY.md` 를 **각 메모리 파일의 frontmatter 에서 생성**하는 CLI + 플러그인입니다.
> Claude Code 는 `MEMORY.md` 를 **앞 200줄·25KB 까지만** 읽는데, 이 도구는 색인을 항상 그 안에 맞추고 넘치는 항목은 지우지 않고 필요할 때 여는 2차 색인으로 보냅니다.
> Claude 가 기본 지침대로 `MEMORY.md` 에 손으로 넣은 줄도 잃지 않고 해당 메모리 파일로 옮깁니다. 표준 라이브러리만 쓰고, 네트워크·외부 프로세스 실행이 없습니다.

Keep Claude Code's `MEMORY.md` within its load limit by generating it — without losing the lines Claude adds by hand.

## Why

Claude Code loads the auto-memory index `MEMORY.md` into every session, but only
[the first 200 lines or 25 KB](https://code.claude.com/docs/en/memory). Entries past that point are
not loaded. A hand-maintained index keeps growing, and trimming it by hand tends to delete the
newest line first, because it is the one that exists nowhere else yet.

cc-memory-index makes the index a build artifact:

- **Each memory file carries its own index line** in its frontmatter (`metadata.idx`). The index
  has one source of truth, so it cannot drift from the memories it describes.
- **`MEMORY.md` (L0) holds only the memories marked `tier: resident`**, and never more than the
  budget. Everything else goes to `index-l1.md` (L1), which L0 links to and Claude opens on demand.
  New memories go to L1 by default, so a growing store does not grow L0.
- **Nothing is dropped.** When resident entries do not fit, the rest are listed under *Overflow*
  in L1 and `suggest` proposes what to demote. Nothing is ever truncated.
- **Claude can keep following its built-in instructions.** When Claude adds a line to
  `MEMORY.md` after writing a memory, the hook moves that line into the memory file's frontmatter
  and regenerates the index.

## How it works

```
memory/                         (the auto-memory directory of one project)
├── feedback_testing.md         metadata.tier: resident, metadata.idx: "[Real DB in tests](…) — …"
├── project_launch.md           no tier → listed in L1
├── MEMORY.md                   L0, generated: resident entries within the budget + a link to L1
└── index-l1.md                 L1, generated: every other memory, then Overflow
```

```markdown
# Memory Index

> Generated by cc-memory-index from each memory file's frontmatter. …

- Not loaded every session: [index-l1.md](index-l1.md) lists every other memory — open it when you need something not listed here.

## Feedback
- [Real DB in tests](feedback_testing.md) — mocks hid a broken migration once
```

After Claude writes `MEMORY.md` or any memory file, the plugin's `PostToolUse` hook rebuilds the
index and tells Claude what happened (for example, that its new line was saved as the memory's
`metadata.idx`).

## Install

Requires Python 3.9+ as `python3` on `PATH`. No other dependencies.

**1. The hook (Claude Code plugin).** In Claude Code 2.1.275 or later:

```
/plugin install cc-memory-index --marketplace oh-namgyu/cc-memory-index
```

or from a shell: `claude plugin marketplace add oh-namgyu/cc-memory-index` then
`claude plugin install cc-memory-index@cc-memory-index`. To try it for one session from a
checkout: `claude --plugin-dir ./cc-memory-index`.

**2. The CLI.** `pipx install git+https://github.com/oh-namgyu/cc-memory-index`, or run
`python3 -m cc_memory_index` from a checkout.

**3. Opt a store in.** The hook does nothing until a store has been written by this tool once.
From your project directory:

```sh
cc-memory-index migrate            # dry run: shows what will be resident, manual and in L1
cc-memory-index migrate --apply    # snapshot first, then convert; undo with migrate --restore
```

For a store with no `MEMORY.md` yet, run `cc-memory-index build` instead.

The store is found from the current directory the way Claude Code finds it (the git repository,
shared by all its worktrees). If you set `autoMemoryDirectory` or `CLAUDE_CODE_PROJECT_DIR_NAME`,
pass `--dir PATH` or set `CC_MEMORY_INDEX_DIR`.

## Commands

| Command | What it does |
|---|---|
| `build [--force]` | Render L0 and L1. Moves hand-added lines into frontmatter first; `--force` backs up and overwrites instead |
| `check` | Exit 1 if the generated files are out of date. Writes nothing |
| `lint` | Broken frontmatter, dangling links and `[[wiki links]]`, unreachable memories, stuck lines. Writes nothing |
| `suggest [--transcripts N] [--apply]` | When L0 is over budget, propose resident memories to demote (largest first, or least mentioned in the last N transcripts); `--apply` demotes them and rebuilds |
| `demote FILE` | Set `tier: indexed` on one memory and rebuild |
| `migrate [--apply \| --restore SNAPSHOT]` | Convert a hand-written `MEMORY.md`. Its opening text (before the first heading or list line) stays as the preamble; other text that is not an index line (code blocks, nested lists, paragraphs) is moved verbatim into a notes memory file |
| `hook` | The `PostToolUse` entry point the plugin calls |

Every command except `hook` takes `--dir PATH` and `--json`; `hook` rejects them. Without
`--json` the whole report goes to stdout when the exit code is 0 or 1 and to stderr otherwise. Exit codes are listed in [docs/DESIGN.md](docs/DESIGN.md#10-commands-and-exit-codes).

## Frontmatter

```yaml
---
name: build-commands
description: How to build and test this repository
metadata:
  type: reference
  tier: resident        # resident = in MEMORY.md; anything else or missing = in index-l1.md
  idx: "[Build commands](build-commands.md) — make test, never make all"
  idx_section: Reference   # default: the capitalised type
  idx_order: 40            # default: 1,000,000; ties break on file name
---
```

Keys may also sit at the top level; unknown keys, including the ones Claude Code adds itself,
are preserved. Without `idx`, the line is built from `name` and `description`.

## Budget and configuration

`.memory-index.json` in the store (all optional):

| Key | Default | Range |
|---|---|---|
| `budget_bytes` | 20480 | 2048–25000 |
| `budget_lines` | 160 | 20–200 |
| `item_max_bytes` | 1024 | 80–4096 |
| `l1_name` | `index-l1.md` | a plain `.md` file name |
| `lock_timeout_s` | 5 | 1–60 |

The defaults sit at about 80% of Claude Code's limits so that its own "near the limit" reminders
stay away. With one entry per line, as Claude Code's own guidance asks, about 135–150 resident
entries of typical length fit (fewer for long or non-ASCII entries); the rest are listed under
*Overflow* in L1 until you demote some (`suggest` proposes which). An entry longer than `item_max_bytes` is listed in L1
instead of being cut.

## Safety

The tool reads and writes one directory and nothing else: no network, no child processes, no
YAML loader or `eval` (a CI gate enforces this). Memory content is treated as untrusted, because
Claude writes it. Links and junctions inside the store are never followed, every write is an
atomic single-file replace checked against what was read, and a crash at any point leaves a valid
store that the next run completes. Details and the remaining limits are in [SECURITY.md](SECURITY.md).

## Limitations

- Verified with Claude Code 2.1.299. The memory frontmatter schema and the transcript format are
  not documented by Claude Code and may change; `check` and `lint` show when the result drifts.
- The hook command is `python3`. On Windows, if `python3` is the Microsoft Store stub, point the
  hook at your Python by editing `hooks/hooks.json` in the installed plugin.
- Two Claude Code sessions writing the same store at the same instant can, in a window of about
  80 µs, lose an index *line* (never a memory file). See [SECURITY.md](SECURITY.md).
